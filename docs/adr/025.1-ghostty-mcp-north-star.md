# ADR-025.1: North Star — The Terminal as an AI-Orchestrated Surface

**Migration note (2026-09-19):** the VT engine is the standalone `@gkoreli/ghostty-vt-js` package. `@gkoreli/ghostty-mcp` remains the AppleScript surface and consumes it for styled reads.

---

## Vision Statement

The terminal stops being a dumb text pipe that AI agents blindly push commands through. It becomes a **fully observable, controllable, reactive workspace** — the AI equivalent of a developer's multi-monitor setup where every screen is visible and every keyboard is reachable.

---

## Where We Are (ADR-025, Done)

```
┌─────────────────────────────────────────────┐
│  AI Agent                                   │
│  Can: list, read, send, spawn, action       │
│  Can: parse VT output structurally (WASM)   │
│  Cannot: react, watch, understand context   │
└─────────────────────────────────────────────┘
```

We have the **primitives**. The agent can see and act. But it's still pull-based — the agent has to explicitly ask "what's on screen?" It can't:
- Get notified when something changes
- Understand what a terminal is *doing* (building? testing? idle?)
- Correlate output across terminals
- Make decisions based on terminal state changes

### The `terminal-screen-emulator` Module

The structural parsing layer is complete and production-ready. It's a standalone, open-source-ready module that emulates a terminal screen in memory:

```typescript
import {
  createTerminalScreen,
  OutputFormat,
} from "@gkoreli/ghostty-vt-js/terminal-screen-emulator";

const screen = await createTerminalScreen({ columns: 120, rows: 40 });
screen.write(rawPtyBytes);

screen.render(OutputFormat.PlainText);    // Just text (for AI agents)
screen.render(OutputFormat.Html);          // Styled HTML (for web UIs)
screen.render(OutputFormat.AnsiEscapes);  // Preserved escapes (for piping)

screen.resize(80, 24);
screen.reset();
screen.dispose();
```

**Architecture:**
```
src/terminal-screen-emulator/
├── index.ts        — Public API (createTerminalScreen, OutputFormat, types)
├── types.ts        — TerminalScreen, TerminalScreenConfig, RenderOptions, TextAttributes
├── emulator.ts     — Core implementation (WASM memory management, struct field writing)
└── wasm-loader.ts  — WASM binary loading, compilation (singleton), instantiation
```

**Key design decisions:**
- Explicit naming: `OutputFormat.PlainText` not `FormatMode.Plain`, `render()` not `format()`
- Full JSDoc on every public type and method (449-line `.d.ts` with examples)
- Self-describing struct layouts via `ghostty_type_json()` — adapts to future Ghostty versions
- Independent instances with isolated WASM memory — no shared state
- Extracted as a standalone package with no application-specific runtime dependencies

## Where We're Going

### Level 1: Reactive Terminal (Watch + Notify)

The agent doesn't poll — it **subscribes** to terminal events.

```typescript
// The agent watches a terminal and reacts to changes
const watcher = ghostty.watch(terminalId, {
  onChange: (diff) => { /* screen content changed */ },
  onCommand: (cmd, exitCode) => { /* a command finished */ },
  onError: (pattern) => { /* error pattern detected */ },
});
```

**Implementation path:**
- Poll-based watcher (every 500ms, diff screen content) — works today
- OSC 133 integration (command start/end markers) — requires shell integration
- Ghostty notification API (`notify-on-command-finish` config) — exists but not wired to AppleScript

**What this enables:**
- "Watch my build and tell me when it fails"
- "If the server crashes, restart it"
- Auto-triage: agent notices a test failure before you do

---

### Level 2: Semantic Terminal Understanding

The agent doesn't just see text — it **understands** what the terminal is showing.

```typescript
const state = await ghostty.analyze(terminalId);
// Returns:
{
  activity: "running-command",        // idle | running-command | awaiting-input
  lastCommand: "npm test",
  exitCode: 1,
  output: {
    errors: ["TypeError: Cannot read property 'id' of undefined"],
    warnings: ["Deprecation: ..."],
    summary: "1 test failed (src/api.test.ts:42)",
  },
  context: {
    cwd: "/workspace/project",
    branch: "feat/user-api",
    env: "development",
  }
}
```

**Implementation path:**
- `terminal-screen-emulator` module (done) gives us styled output → color-based classification (red=error, green=pass)
- OSC 133 gives us command boundaries → know which output belongs to which command
- `pid` + `tty` → `lsof` for CWD, `ps` for process tree
- Pattern matching on common tool outputs (jest, cargo, go test, npm, git)

**What this enables:**
- "What's failing?" → agent reads all terminals, finds the one with errors, explains them
- Automatic context injection: agent knows your CWD, branch, running processes
- Smart routing: agent sends commands to the right terminal based on what it's doing

---

### Level 3: Multi-Terminal Orchestration

The agent manages a **fleet of terminals** as a coordinated system.

```typescript
// Agent orchestrates a build-test-deploy pipeline across splits
const pipeline = ghostty.pipeline([
  { name: "build", cmd: "npm run build", split: "left" },
  { name: "test", cmd: "npm test", split: "right", dependsOn: "build" },
  { name: "deploy", cmd: "npm run deploy", split: "bottom", dependsOn: "test" },
]);

pipeline.on("stage:failed", (stage) => {
  // Auto-fix: read error, generate fix, re-run
});
```

**Implementation path:**
- Spawn + send + read (done) gives us the primitives
- Watcher (Level 1) gives us completion detection
- Semantic understanding (Level 2) gives us success/failure classification
- DAG execution engine coordinates the stages

**What this enables:**
- "Run the full CI pipeline locally and fix whatever breaks"
- Parallel test execution across splits with aggregated results
- Self-healing workflows: build fails → agent reads error → fixes code → re-runs

---

### Level 4: Terminal as Memory

The terminal becomes a **persistent, queryable record** of everything that happened.

```typescript
// Query terminal history semantically
const results = await ghostty.search({
  query: "that error about database connections",
  timeRange: "last 2 hours",
  terminals: "all",
});
// Returns: terminal ID, timestamp, full context, surrounding commands
```

**Implementation path:**
- Scrollback capture via VT parser (parse full scrollback, not just visible screen)
- Index terminal output with timestamps and command boundaries
- Semantic search over terminal history (embeddings or keyword)
- Correlation: link terminal output to git commits, file changes, tickets

**What this enables:**
- "What was that error I saw 30 minutes ago?" → agent finds it across all terminals
- Automatic runbook generation from successful debugging sessions
- Post-mortem: reconstruct exactly what happened during an incident

---

### Level 5: The Agentic Desktop

The terminal is just one surface. The agent orchestrates **all developer surfaces**.

```
┌─────────────────────────────────────────────────────────┐
│  AI Agent (unified workspace awareness)                 │
├─────────────┬──────────────┬──────────────┬────────────┤
│  Terminals  │  Editor      │  Browser     │  Docs      │
│  (ghostty)  │  (LSP/files) │  (devtools)  │  (quip)    │
│             │              │              │            │
│  20 splits  │  open files  │  console     │  specs     │
│  all visible│  diagnostics │  network     │  ADRs      │
│  all writable│ refactoring │  DOM state   │  runbooks  │
└─────────────┴──────────────┴──────────────┴────────────┘
```

This is the end state: the AI agent has the same workspace awareness as a senior developer sitting at a multi-monitor setup — seeing everything, understanding context, acting across surfaces.

ghostty-mcp is the **first surface** we're wiring up. The patterns we establish here (observe → understand → act → verify) become the template for every other surface.

## Immediate Next Steps (What to Build Next)

### 1. `ghostty-mcp watch` — Terminal Watcher (Level 1)

A polling-based watcher that detects changes and emits events:

```bash
ghostty-mcp watch <terminal-id> --interval 500ms --on-change emit
```

Implementation:
- Poll `readTerminal` every N ms
- Diff against previous content
- Detect command completion (prompt reappeared)
- Emit structured events (changed lines, new output, command finished)

**Why first:** This is the foundation for everything reactive. Without it, the agent is always pull-based.

### 2. `readTerminalStyled` — Semantic Read (Level 2)

Wire the `terminal-screen-emulator` module into the read pipeline:

```typescript
import { createTerminalScreen, OutputFormat } from "@gkoreli/ghostty-vt-js/terminal-screen-emulator";

const output = await readTerminalStyled(terminalId);
// Returns structured output with style annotations
// Red text → errors[], Green text → successes[], Bold → identifiers[]
```

Implementation:
- `readTerminal` currently uses `write_screen_file:copy` (plain text)
- Switch to VT format output (Ghostty supports `write_screen_file:paste` which preserves escapes)
- Feed VT bytes through `createTerminalScreen()` → `screen.render(OutputFormat.Html)`
- Parse HTML spans to classify by color/style into semantic categories
- Or use `OutputFormat.AnsiEscapes` and parse SGR codes directly

**Why second:** This turns "agent can read text" into "agent understands output." The `terminal-screen-emulator` module is already built and tested — this step just wires it into the AppleScript read pipeline.

### 3. MCP Server Integration with kiro-cli

Register ghostty-mcp as an MCP server so kiro-cli agents gain terminal tools automatically:

```json
// ~/.config/kiro-cli/mcp.json
{
  "ghostty": {
    "command": "ghostty-mcp",
    "args": ["serve"]
  }
}
```

**Why third:** This is the distribution mechanism. Once it's an MCP server, any agent can use it.

### 4. OSC 133 Command Boundary Detection

Parse OSC 133 markers from terminal output to know exactly where commands start and end:

```
ESC]133;A  ← prompt start
ESC]133;B  ← command start (user pressed Enter)
ESC]133;C  ← command output start
ESC]133;D  ← command finished (with exit code)
```

Implementation:
- Ghostty already emits these (shell integration)
- The VT parser can detect them via the OSC callback
- Map each command to its output region in the scrollback

**Why fourth:** This gives us command-level granularity — know which output belongs to which command, detect success/failure by exit code.

### 5. Upstream Contributions to Ghostty

File the issues/PRs identified in ADR-025:
1. `execute text` command (or `execute: true` flag) — eliminates bracketed paste workaround
2. `working directory` property bug — returns empty despite OSC 7
3. AppleScript API documentation — currently zero docs beyond the sdef
4. `get text` command — read terminal content without clipboard side-effect

**Why fifth:** These improve the foundation. `execute text` alone would simplify our `sendCommand` from a two-step dance to a single call.

## Open Questions

1. **Performance:** Can we poll 20 terminals at 500ms without noticeable overhead? AppleScript is ~50ms per call — that's 10 seconds for a full sweep. Need batching or selective watching.

2. **Security:** Should the MCP server require authentication? Any process on macOS can already control Ghostty via AppleScript, so the security boundary is macOS itself. But the MCP server adds network exposure.

3. **Linux:** Ghostty's GTK version doesn't have AppleScript. What's the bridge? Options: D-Bus, Ghostty's planned IPC protocol, or a PTY-based approach that works without Ghostty-specific APIs.

4. **Scrollback:** `write_screen_file` only captures the visible screen. For Level 4 (memory), we need scrollback access. Options: repeated reads with scroll commands, or lobby for a `get_scrollback` API upstream.

5. **Multi-agent:** If multiple AI agents share the same Ghostty instance, how do they coordinate? Terminal ownership? Locking? Or is it fine to let them race (like humans sharing a screen)?
