# ADR-028.1: Hand-Roll With References; Engine-Blind Core

## Context

ADR-028 chose a hand-rolled glyph-atlas GPU renderer with restty and xterm.js
as references. That decision was challenged twice on 2026-07-29: "why hand-roll
when ready-made, efficient, tree-shakeable libraries exist?" — a fair challenge
that exposed my original survey as incomplete (it had missed both restty and
beamterm). The survey was redone to saturation (further queries return no new
names; full table in ADR-028 "Alternatives considered"). This ADR records the
re-litigated verdict and a structural decision it produced: the renderer core
is engine-blind.

The comparison below is grounded in the referenced source code.

## What each library is truly better at — the parts we copy, not reinvent

- **xterm.js `TextureAtlas`** — a decade of discovered edge cases: glyph page
  management with LRU recycling, four-key caching (char/fg/bg/ext via
  `FourKeyMap`), idle-queue warmup, dim/min-contrast handling, forced 4096px
  texture cap, Safari quirks. This is the file where hand-rollers historically
  bleed; we copy its design decisions wholesale.
- **xterm.js `GlyphRenderer`** — double-buffered instanced attribute arrays:
  you cannot mutate a buffer the GPU is currently reading. A bug class we'd
  otherwise discover the hard way, pre-solved.
- **restty** — the WGSL/GLSL twin-shader structure for a WebGPU+WebGL2 dual
  backend, and procedural box-drawing/braille/powerline rendering (crisper
  than font glyphs, atlas-friendly).
- **beamterm** — proof of the performance ceiling (sub-millisecond at 45k
  cells, one instanced draw call for the whole grid) and a clean
  dynamic-atlas-with-LRU reference. 1.0.0 with a written stability policy —
  the strongest standalone candidate, declined for bus factor 1, an opaque
  Rust→WASM blob in our hottest path, and the two structural reasons below.

## Why the assembled hand-roll beats adopting any of them

1. **The adapter tax lands in the hot loop.** Every library defines its own
   cell API, so adopting one means converting our wasm render state into
   *their* cells every frame — `batch.cell()` across ~5,600 cells is exactly
   the per-cell JS-boundary churn the scrollback memoization work eliminated. (beamterm does offer `batch.text()`/`batch.fill()` run
   batching, but a full-frame refresh still crosses the boundary per run/cell
   and allocates an intermediate model.) Hand-rolled, the pipeline is wasm
   render state → typed-array views → GPU buffer upload, no intermediate
   objects. That is restty's struct-of-arrays insight applied against the
   official C API — something none of them offers, because none of them
   consumes libghostty's render state.
2. **Geometry authority.** beamterm and restty both own their resize model
   (derive cols/rows from pixels; auto-resize CSS). ADR-027 makes the server
   the deciding authority: the renderer must ACCEPT a grid, never derive one.
   Adapting a library around its own geometry opinions costs a real fraction
   of the renderer itself and fights it forever.
3. **Scope asymmetry.** They are general-purpose; we need precisely: monospace
   grid, styles, emoji, box drawing, cursor/selection rects, fed by one known
   engine. Narrower than any of them — which is why ~2k lines is realistic
   where their generality runs 10k+.

Honest gap we accept: restty's text shaping (ligatures, ZWJ emoji families) is
ahead and stays ahead initially. No parity is lost — the canvas 2D renderer
doesn't shape either. Revisit triggers live in ADR-028 (beamterm gains
maintainers/adoption; restty stabilizes 1.x on upstream ghostty).

## Decision: the GPU core is engine-blind

The backend is two layers:

- **`gpu/core/` — engine-blind renderer core.** Imports NOTHING from
  ghostty/wasm/terminal code. Entire input contract: grid dimensions +
  font/cell metrics + a frame as struct-of-arrays typed arrays (codepoints,
  fg, bg, style flags, per-row dirty bits) + cursor/selection rects. Cells in,
  pixels out.
- **`gpu/adapter.ts` — the thin ghostty-facing half.** Implements
  `ITerminalRenderer` (ADR-028's seam), fills the core's typed-array frame
  from wasm render state (batch row reads — never per-cell GridRef), owns
  theme resolution and the geometry handshake (`canvasBox()` in, never
  derived).

This boundary has two effects:
1. The engine-blind boundary **mechanically enforces** reason #1 above: a core
   that cannot import ghostty types can only be fed typed arrays, so per-cell
   object churn cannot creep back in.
2. The core is independently unit-testable (synthetic frames in, atlas/GL
   state asserted — no wasm, no DOM terminal) and independently reusable — a
   candidate standalone package later, serving the package's "de-facto
   standard for adopting Ghostty anywhere" ambition. beamterm's traction for
   exactly this shape (renderer-only, bring your own VT) shows the demand.

Boundary discipline (anti-gold-plating): the core's contract is OUR frame
layout — no pluggable cell formats, no renderer plugin API, no theming DSL.
One consumer defines the contract; generality is earned by a second real
consumer, not speculated.

## Authoritative references and follow-up analysis

Each reference grounds a specific design decision. The final column records a
bounded source investigation for a future implementation increment.

| Reference (exact artifact) | Why it is authoritative / what we take | Follow-up analysis |
|---|---|---|
| xterm.js `addons/addon-webgl/src/TextureAtlas.ts` | THE atlas reference — ships in VS Code. Take: page management, LRU page recycling, `FourKeyMap` glyph keying (char/fg/bg/ext), idle-queue warmup, 4096px forced texture cap, dim/min-contrast handling. | Map its full glyph lifecycle (miss → rasterize → page placement → eviction) and the overflow/page-full path; report the state machine as a diagram + the 5 config constants that matter. |
| xterm.js `addons/addon-webgl/src/GlyphRenderer.ts` | Take: instanced unit-quad vertex layout and DOUBLE-BUFFERED attribute Float32Arrays (GPU owns the in-flight buffer — mutation corrupts frames). | Extract the exact attribute layout (locations, strides) and the buffer-swap protocol; report as a WebGL2 skeleton we mirror. |
| xterm.js `addons/addon-webgl/src/RectangleRenderer.ts` + `DevicePixelObserver.ts` | Take: backgrounds/cursor/selection as a separate untextured-quad pass; dpr-change detection done right. | Enumerate every non-glyph visual (selection, cursor styles, underlines incl. curly, strikethrough, dim) and which pass draws each; report a pass-order spec. |
| restty `src/renderer/shaders/{glyph-wgsl,glyph-gl}.ts` | The only same-engine dual-backend reference. Take: WGSL/GLSL twin-shader structure so WebGPU and WebGL2 share one pipeline shape. | Diff the two shader twins line-by-line; report which parts genuinely diverge (bindings, texture arrays) vs shared — this sizes the WebGPU increment. |
| restty `src/renderer/shapes/` | Take: procedural box-drawing/braille/powerline (geometry, not font glyphs) — crisper, atlas-independent, matches native Ghostty's approach. | Inventory the codepoint ranges it covers and the drawing primitives used; report which ranges our demo actually exercises (tmux borders, btop) to scope increment 1. |
| restty `wasm/src/restty.zig` (CellBuffers) | Take: struct-of-arrays frame layout (parallel typed arrays per attribute) — the zero-object-churn feed. We implement it against the OFFICIAL C API, never a fork shim. | Against our `vt/render-state.ts`: which C-API calls yield batch row data today, what's missing vs restty's SoA, and whether upstream `render.h` has batch getters we don't wrap yet; report the adapter's read plan. |
| beamterm `junkdog/beamterm` (README benchmarks, `beamterm-core` dirty tracking) | Take: the performance ceiling target (sub-ms @ 45k cells, ONE instanced draw call) and chunked dirty-region GPU uploads (changelog 0.17.0). | Read `beamterm-core`'s dirty-region chunking and style-packing into instance data; report the packing bit-layout as a candidate for our instance buffer. |
| native Ghostty `vendor/ghostty/src/renderer/` | The north star and our engine's own opinion. Take: cell shader quad layout, damage model. | Locate the Metal/OpenGL cell shaders and their vertex/instance inputs; report deltas vs xterm.js's layout so our WGSL mirrors upstream where they disagree. |

The atlas analyses block increment 1; shader and native-renderer analyses
block increment 2; the render-state read plan blocks the adapter.
