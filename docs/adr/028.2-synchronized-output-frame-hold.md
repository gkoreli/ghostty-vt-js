# ADR-028.2: Synchronized Output (Mode 2026) as a Frame-Hold Contract

## Problem

TUI applications wrap full-frame redraws in DEC private mode 2026
(`ESC[?2026h` … `ESC[?2026l`) so the terminal never paints a half-drawn
frame. Our render loop ignores it: a rAF tick that lands mid-update paints
whatever the engine holds at that instant — visible tearing on exactly the
applications this terminal hosts; modern Vim and other kitty-protocol
applications use the same framing.

Confirmed against a diff-based TUI producer that emits `ESC[?2026l` at
frame end; the engine side already exists — libghostty
parses the mode (`modes.h:92`, `GHOSTTY_MODE_SYNC_OUTPUT =
ghostty_mode_new(2026, false)`) and our wrapper can query it via the
existing `Terminal.getMode(value, isAnsi)` plumbing.

## Decision

Honor 2026 as a **frame-hold contract in the frame scheduler** — the layer
that decides *whether* to paint — never inside a renderer backend:

- Each rAF tick, before any render-state side effects, consult the engine:
  if `getMode(SYNC_OUTPUT)` is true, skip the paint and keep the last
  presented frame.
- The skip must occur BEFORE `beginFrame()`/dirty-state consumption. Dirty
  flags are the engine's record of what the eventual paint must cover;
  consuming them on a skipped tick loses rows from the post-hold frame.
- **Safety valve:** a held frame is force-painted after ~150ms (the de-facto
  cap from kitty's synchronized-output spec, which this mode descends from).
  A misbehaving app that sets 2026 and never clears it degrades to today's
  behavior, never to a frozen terminal.
- The hold decision is ONE pure function (active-mode flag + hold-start
  timestamp + now → paint/skip), unit-testable without DOM, used by the one
  rAF loop. It applies uniformly to every `ITerminalRenderer` backend —
  CanvasRenderer today, the ADR-028 GPU backend tomorrow — because holding
  frames is scheduling, not painting.

## Why scheduler, not renderer

The seam contract (ADR-028) says `render()` is called every frame and
backends self-limit via dirty tracking. Teaching each backend about 2026
would duplicate the policy per backend and re-couple them to the engine's
mode set — the exact coupling ADR-028.1's engine-blind core forbids. One
authority: the scheduler holds; renderers paint what they're asked to.

## Consequences

- TUI applications get atomic frames; the demo can exercise framed redraws
  as a regression scenario.
- The GPU backend inherits the behavior for free at the loop level.
- The scrollback memo and dirty tracking are unaffected: a hold defers reads
  entirely rather than snapshotting them.
- Future: mode 2026 state could travel to `TerminalSessionHost` mirrors for
  server-side frame-coherent snapshots (styled reads in ghostty-mcp) — out
  of scope here.

## Cross-references

- **ADR-028 / 028.1** — the seam and engine-blind core this contract must
  not violate (hence scheduler placement).
- **kitty synchronized-output spec** — the ~150ms max-hold convention we
  adopt as the safety valve.
- **Diff-based TUI producers** — establish the motivating behavior: redraws
  framed by `?2026h/l`.
- **libghostty `include/ghostty/vt/modes.h:92`** — engine-side parsing
  already done; this ADR is consumer-side only.
